The numbers behind the experiment

One empty repo, five months, and a team that no longer writes code.

The first commit landed in late August 2025. The scaffold — CI, formatters, package manager, framework, even the initial AGENTS.md — was generated by Codex CLI using GPT‑5. There was no human-written anchor. The repository has been shaped by the agent from line zero.

Throughput increased as the team grew from three engineers to seven. The product has hundreds of internal users, external alpha testers, and daily power users. Built, the authors estimate, in one-tenth the time it would have taken by hand.

The new job description

Humans steer.
Agents execute.

Early progress was slower than expected — not because Codex was incapable, but because the environment was underspecified. The agent lacked the tools, abstractions, and internal structure required to make progress toward high-level goals.

The primary job of the engineering team became enabling the agents to do useful work. When something failed, the fix was almost never “try harder.” Human engineers stepped in and asked a different question entirely.

“What capability is missing, and how do we make it both legible and enforceable for the agent?”

In practice, that meant working depth-first: breaking down larger goals into smaller building blocks — design, code, review, test — prompting the agent to construct those blocks, then composing them into unlocks for more complex tasks.

A cautionary tale

The one-big-manual antipattern.

Teams reach for a monolithic instruction file and learn the hard way: context is scarce, guidance decays, drift is invisible. We tried it. It failed in predictable ways.

Context is scarce

A giant instruction file crowds out the task, the code, and the relevant docs.

The agent either misses key constraints or starts optimizing for the wrong ones. Every token spent on the manual is a token not spent on the problem.

Guidance decays

When everything is “important,” nothing is.

Agents pattern-match locally instead of navigating intentionally. The manual rots instantly — becoming a graveyard of stale rules that humans stop maintaining and agents can’t trust.

The fix

Treat AGENTS.md as a table of contents, not an encyclopedia. Roughly 100 lines. A map. Pointers to deeper sources of truth — enforced mechanically, gardened continuously.

Bootable per-git-worktree. Logs queryable with LogQL. Metrics queryable with PromQL. Every task runs on a fully isolated instance — torn down on completion. A single Codex run routinely works on a task for upwards of six hours. Usually while the humans are sleeping.

On legibility

If the agent can’t see it, it effectively doesn’t exist.

From the agent’s point of view, anything it can’t access in-context while running effectively doesn’t exist. Knowledge that lives in Google Docs, chat threads, or people’s heads is not accessible to the system. Repository-local, versioned artifacts — code, markdown, schemas, executable plans — are all it can see.

That Slack discussion which aligned the team on an architectural pattern? If it isn’t discoverable to the agent, it’s illegible in the same way it would be unknown to a new hire joining three months later.

The team favored dependencies that could be fully internalized. Boring technologies tend to be easier for agents to model — composability, API stability, strong training-set representation. In some cases it was cheaper to have the agent reimplement subsets of functionality than to wrestle with opaque upstream behavior.

Case in pointRather than pull in a generic p-limit-style package, the agent authored its own map-with-concurrency helper — tightly integrated with OpenTelemetry instrumentation, 100% test coverage, behaving exactly as the runtime expects.

Pulling more of the system into a form the agent can inspect, validate, and modify directly increases leverage — not just for Codex, but for the other agents (Aardvark among them) that work on the same codebase.

The Architecture DeskInvariants, not implementationsPage 8

Enforce boundaries. Allow autonomy.

The kind of architecture you usually postpone until you have hundreds of engineers. With coding agents, it’s an early prerequisite.

By the Harness Team · Illustrated with custom linters
Forward-only dependency layers per business domainTypes → Config → Repo → Service → Runtime → UI

Documentation alone does not keep a fully agent-generated codebase coherent. The team built the application around a rigid architectural model. Each business domain is divided into a fixed set of layers, with strictly validated dependency directions and a limited set of permissible edges.

These constraints are enforced mechanically via custom linters — Codex-generated, of course — and structural tests. Cross-cutting concerns such as auth, connectors, telemetry, and feature flags enter through a single explicit interface called Providers. Anything else is disallowed.

A small set of “taste invariants” travels with the layering: structured logging is statically enforced; naming conventions for schemas and types are checked; file-size limits and reliability requirements are codified. Because the lints are custom, error messages inject remediation instructions directly into agent context.

In a human-first workflow these rules might feel pedantic. With agents they become multipliers: once encoded, they apply everywhere at once. The team is explicit about where constraints matter and where they do not — boundaries, correctness, reproducibility are non-negotiable; stylistic expression within those walls is left to the agent.

The resulting code does not always match human stylistic preferences, and that is okay. As long as the output is correct, maintainable, and legible to future agent runs, it meets the bar. Human taste is fed back continuously: promoted into documentation, then into tooling, then into lint.

The repository now operates with minimal blocking merge gates. Pull requests are short-lived. Test flakes are often addressed with follow-up runs rather than blocked indefinitely. In a system where agent throughput far exceeds human attention, corrections are cheap and waiting is expensive.

The threshold

End-to-end, from one prompt.

As more of the development loop was encoded into the repository — testing, validation, review, feedback handling, recovery — Codex crossed a threshold. Given a single prompt, the agent now drives the entire arc of a feature.

01Validate

Inspect the current state of the codebase before touching anything.

02Reproduce

Reproduce the reported bug in an isolated worktree instance.

03Record

Capture a video demonstrating the failure for the record.

04Implement

Write the fix, guided by repository knowledge and layer boundaries.

05Re-validate

Drive the application to confirm the fix actually resolves the issue.

06Re-record

A second video, demonstrating the resolution in context.

07Open PR

Request self-review, local agent review, and cloud agent review.

08Iterate

Respond inline to agent & human feedback. Detect & repair build breakage.

09Escalate / Merge

Escalate to a human only when judgment is required. Otherwise — squash & merge.

This behavior depends heavily on the specific structure and tooling of this repository and should not be assumed to generalize without similar investment — at least, not yet.
